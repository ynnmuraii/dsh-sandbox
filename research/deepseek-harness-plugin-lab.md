# Лаборатория разработки плагинов DeepSeek Harness

> **Срез и оговорки.** Ниже разделены наблюдаемые контракты и рекомендации. DeepSeek Harness прямо называет себя developer preview и предупреждает о compatibility-breaking changes ([README](https://github.com/deepseek-ai/deepseek-harness/blob/master/README.md)); upstream Cordis также предупреждает, что его API активно развивается ([Cordis README](https://github.com/cordiverse/cordis/blob/main/README.md)). Поэтому лаборатории нужно фиксировать ревизии Harness и vendored Cordis, а не считать `master` стабильным SDK. Сам Harness вендорит Cordis под `@deepseek-ai/*`, фиксирует upstream commit и перечисляет локальные изменения Loader/Include/HMR ([vendor/README](https://github.com/deepseek-ai/deepseek-harness/blob/master/vendor/README.md)).

## Краткий вывод о внешней разработке

**Наблюдение.** Официально описаны **два** пути. Для быстрой разработки предлагается source checkout Harness и локальный модуль, подключаемый `--patch`; tutorial начинает именно с checkout, показывает TypeScript-файл с `export const name`/`export function apply(ctx)`, а в overlay указывает абсолютный путь к модулю ([Your first plugin](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/index.md)). Для распространения описан самостоятельный npm/Git/local-пакет-бандл: его `package.json` объявляет `dsh.bundle.patch`, patch вставляет строку с именем пакета, а `dsh plugin --profile <name> add ...` устанавливает пакет в профиль ([Package and install a plugin](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/publish.md)).

**Вывод.** Внешние плагины не ограничены исходным checkout: официально поддержан installable bundle через профиль. Но source overlay — документированный путь авторинга и проверки живого кода; отдельный публичный SDK/генератор проекта в просмотренных официальных материалах не заявлен, поэтому это следует считать [ИНФЕРЕНЦИЯ] о границе документации, а не доказательством отсутствия такой возможности.

## 1. Авторинг, жизненный цикл и эффекты

**Наблюдение.** Плагин — TypeScript/JavaScript-модуль с `apply(ctx, config?)`; поддерживаются function-, object- и class-формы. В function-форме `name` и `apply` экспортируются именованно; object/class обычно экспортируются как default. Конфигурация описывается экспортом `Config` и одноимённой Schemastery-схемой: Loader валидирует вход и применяет defaults ([first-plugin tutorial](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/index.md), [config tutorial](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/config.md)). Внутреннее правило Harness уточняет: function plugin не должен иметь default export, иначе Loader может потерять его namespace (`name`/`inject`/`Config`/`apply`) ([packages/AGENTS.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/AGENTS.md)).

**Наблюдение.** Каждый экземпляр получает Cordis Fiber и проходит `PENDING → LOADING → ACTIVE` либо `FAILED`; при удалении — `UNLOADING → DISPOSED`. `apply` не запускается до готовности обязательных сервисов; исчезновение обязательного провайдера выгружает зависимый Fiber, а появление провайдера активирует его снова ([plugins and lifecycle](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/framework/index.md)).

**Наблюдение.** Регистрации через `ctx` являются эффектами: `ctx.on()` снимает listener при выгрузке, регистрации tools/LLM-adapter также принадлежат Fiber, а `ctx.effect(() => disposer)` связывает внешний ресурс с явным disposer ([plugins and lifecycle](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/framework/index.md), [events](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/framework/events.md)). В upstream Cordis Fiber хранит disposers и при unload обходит их в обратном порядке; asynchronous disposers могут выполняться конкурентно, поэтому порядок, важный для корректности, следует объединять в один disposer с последовательным `await` ([Fiber source](https://github.com/cordiverse/cordis/blob/main/packages/core/src/fiber.ts)). `ctx.plugin(child)` создаёт дочерний Fiber, жизненный цикл которого привязан к родителю ([plugins and lifecycle](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/framework/index.md)).

## 2. Сервисы, зависимости и композиция

**Наблюдение.** Сервис — именованная возможность в `ctx` (`ctx.tools`, `ctx.llm`, `ctx.agents` и т. п.). `inject` — декларация обязательных зависимостей; необязательную зависимость рекомендуют получать через `ctx.get(name)` в месте использования, не обращаясь к недекларированному proxy-свойству ([services and dependencies](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/framework/service.md), [packages/AGENTS.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/AGENTS.md)). Service-класс регистрирует предоставление имени в контексте; тип `ctx.<key>` оформляется TypeScript declaration merging ([Cordis Service source](https://github.com/cordiverse/cordis/blob/main/packages/core/src/service.ts)). Группы Loader могут изолировать один и тот же ключ, чтобы разные поддеревья получили разные экземпляры ([services and dependencies](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/framework/service.md)).

**Наблюдение.** Typed events — основной слабосвязанный канал. `emit` наблюдает без результата, `waterfall` оборачивает результат и требует `next()` для делегирования, `serial` выполняет по порядку с ожиданием, `parallel` выполняет слушателей параллельно; `ctx.on()` сам является эффектом и снимается при unload ([event system](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/framework/events.md), [Cordis Events source](https://github.com/cordiverse/cordis/blob/main/packages/core/src/events.ts)).

**Наблюдение.** Для заменяемой capability официальная модель Harness разделяет Service Definition, Service Provider и Consumer; провайдер и consumer зависят только от definition и могут развиваться/заменяться независимо ([three-role capability design](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/practice/index.md)).

## 3. Конфигурация, Loader и профили

**Наблюдение.** Loader entry содержит стабильный `id`, `name` модуля, `config`, `inject`, `disabled`, а также group/isolation metadata. Include читает YAML/JSON и поддерживает `!!js`; Harness документирует lazy interpolation: `config` вычисляется после активации объявленных injections, а `disabled` проверяется на каждом mount decision ([Cordis Entry source](https://github.com/cordiverse/cordis/blob/main/packages/loader/src/config/entry.ts), [Cordis primer](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-primer.md)).

**Наблюдение.** Профиль — каталог `$DSH_HOME/profiles/<name>` с `package.json` и `cordis.patch.yml`. В его `package.json` поле `dsh.profile.bundles` задаёт порядок bundle-пакетов; bundle объявляет в своём `package.json` `dsh.bundle.patch`. Эффективное дерево строится над пустым списком: bundle patches по порядку, профильный patch, home-level patch, затем `--patch` overlays. Поздний слой выигрывает по строке; patch заменяет весь `config` целиком, а не делает deep merge, и может вставлять строки ([app-boot Profiles](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/boot/app-boot/README.md#profiles), [profile implementation](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/boot/app-boot/src/profile.ts), [CLI reference](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/reference/README.md)). `dsh --profile ... --dump-config` позволяет увидеть результат без boot ([CLI reference](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/reference/README.md)).

**Наблюдение.** `dsh plugin --profile <name> <pnpm args>` запускает pnpm в каталоге профиля; поддерживаются registry, Git и локальные `./path`, `file:` и `link:` спецификации. Относительные path specs якорятся к invoking directory, поэтому `add ./hello-plugin` из checkout подключает checkout, а не каталог самого профиля. После успешной операции Harness добавляет в `dsh.profile.bundles` только зависимости, чей манифест содержит `dsh.bundle`; bundle-less dependency остаётся обычной библиотекой ([plugin manager source](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/src/plugin.ts), [publish tutorial](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/publish.md)).

## 4. Hot reload

**Наблюдение.** При изменении конфигурации framework выгружает старый экземпляр и загружает новый; effect-owned registrations не остаются от старого экземпляра ([config tutorial](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/config.md)). Upstream `@cordisjs/plugin-hmr` классифицирует changed modules и их dependents как accepted/declined, очищает ESM и CJS caches, повторно импортирует plugin entry, удаляет старый runtime и регистрирует новый. Ошибка импорта или регистрации откатывает caches и восстанавливает прежний plugin ([HMR source](https://github.com/cordiverse/cordis/blob/main/packages/hmr/src/index.ts)). Изменение loader config-файла обновляет Include; DSH дополнительно наблюдает профильный и home `cordis.patch.yml` и оставляет последнюю рабочую композицию при ошибке чтения/парсинга/кандидатного Loader tree ([app-boot README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/boot/app-boot/README.md#profiles), [vendor modifications](https://github.com/deepseek-ai/deepseek-harness/blob/master/vendor/README.md)).

**Вывод.** HMR нельзя считать автоматически одинаковым для двух путей: стандартные Cordis HMR roots по умолчанию игнорируют `node_modules`, а сбор зависимостей также исключает modules внутри `node_modules` ([HMR source](https://github.com/cordiverse/cordis/blob/main/packages/hmr/src/index.ts)). Поэтому внешнему пакету, установленному в профиль, нужна отдельная проверка наблюдаемости исходников; локальный `--patch` с source path и установленный built bundle следует тестировать как разные режимы. Это [ВЫВОД] из наблюдаемого фильтра, а не обещание документации.

## 5. Пакетирование и тестирование

**Наблюдение.** Минимальный внешний bundle содержит ESM `package.json` (`name`, `version`, `type`, `main`, `files`, `dsh.bundle`), patch YAML и entry module. Пользователь может установить registry-пакет, Git checkout или local package; пакет без `dsh.bundle` намеренно устанавливается только как plain dependency ([publish tutorial](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/publish.md)). Git-install получает sources, поэтому TypeScript bundle должен сам собрать entry points через `prepare`; pnpm ≥10 требует явного `allowBuilds` в profile `pnpm-workspace.yaml`. npm-пакет с уже собранным `lib/` или tarball этой установки не требует ([publish tutorial](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/publish.md)).

**Наблюдение.** Внутренний workspace checklist строже: `packages/<group>/<pkg>`, ESM `main`/`types`/`exports`, Cordis в peer и dev dependencies, зеркалирование DSH peer dependencies, README с API/extension points и регистрация ровно в одном Host/Client aggregate ([adding a workspace package](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cookbook/adding-a-package.md), [development guide](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/development.md)). Эти требования относятся к monorepo packages, не автоматически к самостоятельному npm bundle.

**Наблюдение.** Политика тестов требует package-local Vitest suites под `tests/**`, HMR-safety test для каждого registry (dispose contributing Fiber и проверить cleanup), а product-visible plugin — non-unit real-composition test: поднять test-only `cordis.yml` через Loader и app/process, мокать только внешние/недетерминированные границы и проверять model-visible, durable или user-visible результат. Для published artifact нужен отдельный built-entry smoke под обычным Node; source-plane tests не должны случайно подхватывать stale `lib/` ([testing policy](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/testing.md), [packages/AGENTS.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/AGENTS.md)).

## 6. Что из Cordis paper задаёт границы лаборатории

**Наблюдение.** Paper выделяет две ортогональные гарантии: temporal composability — полное восстановление side effects после удаления компонента; spatial composability — декларативное и реактивное управление зависимостями. Revertible effect возвращает новое состояние и inverse, reactive coeffect уведомляет компонент об изменении удовлетворённости его dependency specification; Cordis реализует это через effects, fibers, Loader и HMR ([paper.pdf, §§3.1–3.3](../paper.pdf#page=9), [paper.pdf, §5](../paper.pdf#page=54)).

**Наблюдение.** Граница системы проходит по каждой локации: она «внутри» только если система эксклюзивно изменяет её и может восстановить прежнее состояние; acquisition (descriptor, allocation, child process) можно сделать tracked/revertible, а emission наружу обычно уже является необратимой операцией. Для emission paper предлагает withholding до commit или application-level compensation ([paper.pdf, §6.1](../paper.pdf#page=67)).

**Наблюдение.** Для нескольких реализаций сервиса paper различает exclusive binding и service broker; broker позволяет сосуществование провайдеров, load balancing и rolling update без обязательной реактивации каждого consumer ([paper.pdf, §6.2](../paper.pdf#page=68)). Capability mediation через declared dependencies похожа на capability security, но языковой контроль не заменяет sandbox для недоверенного кода ([paper.pdf, §6.3](../paper.pdf#page=69)). Цикл взаимных dependencies оставляет компоненты inactive; его обычно устраняют декомпозицией интеграционных компонентов ([paper.pdf, §6.5](../paper.pdf#page=71)). Номинальный key сам по себе не защищает от interface drift и key collision; paper отмечает peer dependencies как текущий компромисс Cordis и обсуждает namespacing/structural compatibility ([paper.pdf, §6.6](../paper.pdf#page=72)).

## 7. Сравнение двух линий для внешнего workspace [РЕКОМЕНДАЦИЯ]

| Критерий | Source overlay | Installable bundle |
|---|---|---|
| Что документировано | Checkout Harness, локальный TS/JS module, абсолютный path в `--patch` | Отдельный пакет с `dsh.bundle.patch`, установленный в profile через `dsh plugin` |
| Главный объект проверки | Поведение исходного модуля против конкретного Harness checkout | Реальный npm/Git/local package boundary, manifest, patch layer и built entry |
| Конфигурация | `--patch` слой; path остаётся явным и не меняет profile base directory | Пакет владеет своей patch layer; профиль владеет порядком bundles и пользовательскими overrides |
| HMR-риск | Источник виден как обычный project path, но watcher/root всё равно нужно проверить | `node_modules` фильтруется стандартным HMR, поэтому live source reload нельзя предполагать |
| Артефакты | Зависит от source-launch/build контрактов checkout | Git-пакету нужен self-contained `prepare` или заранее собранный npm/tarball |

Эта таблица сравнивает документированные границы, а не предлагает конкретное дерево каталогов или реализацию лаборатории.

## Итоговые ограничения, которые дизайн лаборатории обязан уважать

1. **Фиксировать версии.** Записывать Harness revision, vendored Cordis commit, Node/pnpm и режим запуска; upstream API нестабилен ([DSH README](https://github.com/deepseek-ai/deepseek-harness/blob/master/README.md), [vendor manifest](https://github.com/deepseek-ai/deepseek-harness/blob/master/vendor/README.md)).
2. **Разделять два boundary.** Не смешивать вывод source overlay с доказательством, что опубликованный bundle устанавливается и запускается; проверять source и built artifact отдельно.
3. **Считать `inject` контрактом.** Не полагаться на порядок строк Loader; проверять provider absent/present/replacement и не прятать обязательные зависимости в `ctx.get()`.
4. **Доказывать reversibility.** Любой `ctx.on`, registry registration и внешний resource должен иметь Fiber-owned disposer; order-dependent async teardown держать в одном последовательном disposer ([lifecycle](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/framework/index.md)).
5. **Не обещать rollback за пределами системы.** Сетевые/persistent emissions маркировать как non-revertible и отдельно описывать compensation/commit boundary ([paper.pdf, §6.1](../paper.pdf#page=67)).
6. **Сохранять patch semantics.** Тестировать порядок слоёв, stable ids, whole-config replacement, `!!js` и `--dump-config`; не предполагать deep merge ([CLI reference](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/reference/README.md)).
7. **Тестировать HMR атомарно.** Проверять cleanup старого Fiber, новый apply, provider disappearance, invalid config/import и rollback; для внешнего package path отдельно проверять, попадает ли исходник в watcher.
8. **Тестировать реальный entry path.** Unit-тест `ctx.plugin()` не заменяет Loader/app/process composition и built-package smoke ([testing policy](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/testing.md)).
9. **Не смешивать Cordis instances/scopes.** [Рекомендация] Для standalone TypeScript package использовать scoped Harness Cordis peer-границу и совместимые DSH peer ranges, а не случайно подтягивать второй upstream instance; основание — vendor rescope/fallback и внутренний package invariant ([vendor/README](https://github.com/deepseek-ai/deepseek-harness/blob/master/vendor/README.md), [adding a workspace package](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cookbook/adding-a-package.md)).
10. **Изолировать capability roles.** Когда definition/provider/consumer меняются независимо, держать их контракт и зависимости раздельными; проверять provider swap через один key и не допускать циклических declarations ([three-role design](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/practice/index.md), [paper.pdf, §§6.5–6.6](../paper.pdf#page=71)).
11. **Считать install scripts недоверенным кодом.** Git `prepare` и `allowBuilds` выполняются на машине пользователя до запуска Harness; pin commit и разрешать сборку только для проверенного исходника ([publish tutorial](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/publish.md)).
12. **Не выдавать рекомендации за upstream contract.** Всё, что касается конкретной layout-схемы, watcher roots, тестового matrix или sandbox boundary, в лаборатории должно быть явно помечено как [РЕКОМЕНДАЦИЯ]/[ИНФЕРЕНЦИЯ] и проверено против зафиксированной ревизии.
