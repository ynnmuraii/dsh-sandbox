# Portable DSH Plugin Development Skill Design

## Purpose

Stage 2 gives any agent harness that recognizes the cross-runtime `.agents/skills`
convention one stable entrance into `dsh-lab`. The entrance explains what the
forge provides, routes the agent to the canonical contracts, and recommends a
useful plugin-development loop without taking ownership of the agent's planning,
memory, SDD, delegation, or orchestration.

The only projected skill is:

```text
.agents/skills/dsh-plugin-development/SKILL.md
```

No `.dsh`, `.codex`, root `skills/`, or per-plugin skill mirror is introduced.

## Scope

This stage includes:

- one concise, generated `dsh-plugin-development` skill;
- one canonical skill body inside `context/*`;
- deterministic generation and line-ending handling;
- regeneration through the existing `lab sync-context` authoring command;
- read-only drift detection in `lab doctor` and the test suite;
- automated contract tests and a fresh-agent behavioral evaluation.

This stage does not include:

- UI sessions or browser automation;
- real API credentials or release automation;
- agent memory, task state, approval state, or SDD state;
- an orchestration engine or a mandatory development methodology;
- plugin-local copies of the skill;
- a new top-level `lab skill` or `lab sync-skill` command.

## Source of truth and projection

`context/*` remains the only editable source of shared forge knowledge. The
canonical body for the entry skill is:

```text
context/dsh-plugin-development-skill.md
```

That file contains the Markdown body beginning with `# DSH Plugin Development`.
It has no YAML frontmatter and no generated digest. The generator supplies those
mechanical parts.

The generated file has this shape:

```markdown
---
name: dsh-plugin-development
description: Use when creating, studying, debugging, or verifying a DeepSeek Harness plugin in dsh-lab.
---

# DSH Plugin Development

> Generated from `context/*`; do not edit this file directly.
> context version: <12 lowercase hex characters>
> regenerate with `pnpm lab sync-context`

<canonical body content after its first H1 line>
```

The canonical body must start with exactly `# DSH Plugin Development`. The
renderer moves the generated note immediately after that first heading and then
appends the remainder of the canonical body, so the projection contains one H1.
It must produce one final newline and LF line endings. A
fresh clone on Windows must not become stale merely because Git or an editor
materialized CRLF; comparison normalizes CRLF and lone CR to LF before checking
the canonical bytes.

The skill body is a router, not a concatenation of every context document. It
must stay concise and point the agent to the live canonical documents:

- `context/harness-contracts.md` for public integration contracts;
- `context/cordis-model.md` for Fiber/effect/inject behavior;
- `context/plugin-anatomy.md` for standalone package shape;
- `context/testing-policy.md` for test levels and HMR safety;
- `context/compatibility.md` for target claims and pins;
- `docs/using-the-lab.md` for command recipes.

This keeps automatic skill loading cheap while preserving the full contracts as
on-demand references.

## Skill behavior

The skill presents the lab as an environment owned by the working agent. It
must tell the agent to:

1. identify the plugin by catalog name or `--path`;
2. read the relevant canonical contracts before changing production code;
3. inspect the current package and target claims;
4. use `lab dev` for live source/HMR work;
5. use `lab verify` for source and bundle acceptance;
6. use `lab status` to interpret current, stale, and missing evidence;
7. leave remote publication, release, secrets, and plugin Git decisions to an
   explicitly authorized workflow.

The skill may recommend SDD, specifications, plans, TDD, reviews, delegation,
or harness-native skills. It must explicitly say these are choices made by the
agent and its host harness. It must not require a named harness, require
subagents, store workflow stage, or make the lab advance an approval state.

The YAML `description` describes only when to load the skill. It does not
summarize the workflow, so a host cannot treat the frontmatter as a shortcut for
reading the skill.

## Deterministic context identity

`tooling/src/sync.ts` owns a reusable context digest function. It normalizes
line endings and hashes the ordered context document contents with unambiguous
boundaries. Both `snapshotContext` and the agent-skill renderer use that exact
digest.

`contextDocuments(root)` keeps its current sorted filename order. Adding,
removing, or changing any `context/*.md` file changes the digest and therefore
makes both plugin snapshots and the generated skill stale.

The generated skill does not embed target versions, catalog entries, absolute
paths, plugin names, or upstream commit IDs. Those remain live data owned by
`workbench/compatibility.yaml`, `catalog.yaml`, and the CLI.

## Authoring command

`pnpm lab sync-context [name|--all]` remains the single explicit authoring
command for context projections. After validating every requested plugin target
up front, it:

1. renders the canonical skill in memory;
2. writes `.agents/skills/dsh-plugin-development/SKILL.md` only when its
   normalized content differs;
3. writes requested plugin `.dsh-lab/shared-context.md` snapshots using the
   existing behavior;
4. returns one result per written or current projection so the CLI prints
   `synced` or `current` for both root skill and plugin snapshots.

Calling `pnpm lab sync-context` without a name is the minimal way to regenerate
only the root skill. Calling it with a name or `--all` also regenerates the root
skill. If any requested plugin repo is missing or invalid, validation fails
before either projection is written.

`lab new` does not regenerate the root skill. A missing root skill is repository
drift, not a side effect for plugin creation to conceal.

## Doctor and CI drift gates

`lab doctor` renders the expected skill entirely in memory and never writes it.
It emits an error when the generated file is missing or differs after newline
normalization. The diagnostic names the exact path and remediation:

```text
stale agent skill: <path> (run `lab sync-context`)
```

The normal test suite also compares the committed projection with the in-memory
renderer. This makes drift fail in CI even when CI does not invoke `lab doctor`.

The gates detect manual edits, missing files, canonical body changes, and changes
to any other context contract. They do not inspect or create host-specific
skill locations.

## Mutation and safety boundaries

- The renderer is pure and performs no filesystem writes.
- `doctor` is read-only.
- Only the explicit `sync-context` authoring command writes the projection.
- The projection path is a fixed descendant of the forge root; no user input
  participates in it.
- Generation reads Markdown from `context/*` only and never reads environment
  variables, credentials, catalog content, or plugin source.
- Sync validates all plugin repositories before writing anything, preserving
  the existing no-partial-sync rule.
- Production plugin code and plugin Git state remain untouched except for the
  already-authorized shared-context snapshot write requested by the command.

## Test strategy

The controller owns and commits all tests before production implementation.
Luna implementers may change production and documentation files only; test
changes require controller approval.

Automated tests cover:

- renderer determinism, frontmatter, one H1, one final newline, and LF output;
- shared context digest stability across LF/CRLF and sensitivity to content;
- concise routing content and all canonical document references;
- advisory SDD/orchestration language rather than mandatory harness coupling;
- absence of dynamic target pins, absolute paths, and extra skill mirrors;
- sync-only-root behavior, named/all behavior, idempotence, and preflight
  failure before any write;
- doctor clean, missing, tampered, and context-changed cases;
- CLI help and `synced`/`current` output;
- real-repository equality between the committed generated file and renderer.

The behavioral evaluation uses fresh Luna contexts:

1. baseline prompt without the skill records whether an agent misses the
   canonical contracts or treats the lab as a human workflow engine;
2. the same prompt with the generated skill verifies that the agent routes to
   `context/*`, chooses its own method, and uses the correct lab commands;
3. an adversarial prompt asking the lab to remember approval state verifies
   that the agent keeps workflow state in its own harness rather than inventing
   lab state.

These evaluations do not grant write access and do not replace automated tests.

## Acceptance criteria

Stage 2 is accepted when:

1. exactly `.agents/skills/dsh-plugin-development/SKILL.md` exists as the only
   skill projection;
2. its editable body lives in `context/dsh-plugin-development-skill.md`;
3. `pnpm lab sync-context` regenerates it deterministically and is idempotent;
4. `pnpm lab doctor` reports missing or stale skill content without writing;
5. the committed projection equals the renderer output;
6. the skill recommends but does not enforce SDD or orchestration;
7. all automated tests and typecheck pass;
8. fresh-agent behavioral evaluation demonstrates the intended routing;
9. final verification in the main checkout passes `pnpm test`,
   `pnpm typecheck`, and `pnpm lab doctor` after explicit context sync.
